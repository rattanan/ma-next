# แผนปรับ UX/UI ระบบ MA Next

วันที่จัดทำ: 5 กันยายน 2026  
สถานะ: แผนสำหรับนำไปพัฒนาต่อ — ยังไม่ได้ปรับหน้าจอตามแผนนี้

## 1. เป้าหมายและแนวทาง

ทำให้ผู้ใช้เปิดระบบแล้วรู้ว่าต้องทำอะไรต่อ ค้นหาเอกสารได้เร็ว และทำงานหลักจบได้โดยไม่ต้องเปิดหลายหน้า พร้อมทำให้หน้าตาทุกโมดูลสม่ำเสมอ อ่านง่าย และรองรับมือถือสำหรับงานภาคสนาม

เริ่มจาก Dashboard, Work Order และการอนุมัติ PR/PO แล้วขยายรูปแบบที่ผ่านการใช้งานจริงไปยังคลังและข้อมูลหลัก ใช้ [design.md](./design.md) เป็นฐานด้านภาพลักษณ์ และใช้เอกสารนี้กำหนดลำดับการพัฒนา เมื่อข้อเสนอใหม่ต่างจาก design.md ให้ปรับเอกสารทั้งสองให้ตรงกันในงานนั้น

หลักปฏิบัติ:

- แสดงข้อมูลสำหรับตัดสินใจก่อนรายละเอียดรอง
- มีปุ่มหลักที่ชัดเจนตามสถานะและสิทธิ์จริงของผู้ใช้
- ใช้ศัพท์ไทยให้สม่ำเสมอ โดยคงเลขเอกสารและรหัสที่จำเป็นต่อการอ้างอิง
- รักษาค่าตัวกรองและข้อมูลกรอกเมื่อกลับหน้าหรือเกิดข้อผิดพลาด
- ใช้ component และ tokens ร่วมกัน เพื่อลดความแตกต่างระหว่างโมดูล
- คง business rules, การตรวจสิทธิ์ฝั่ง server และ workflow เดิม หากต้องเพิ่มความสามารถ backend ให้แยกเป็นงานที่มีเกณฑ์ตรวจรับของตัวเอง

| เอกสารสถานะ | บางส่วนล้าหลังโค้ด; migration รับของในไฟล์คือ `0011_purchase_order_receipts` | ตรวจฐานข้อมูล DEV และปรับเอกสารก่อนอ้างว่า deploy ครบ |

## 3. ผู้ใช้และงานหลัก

| ผู้ใช้ | งานที่ต้องทำให้สะดวกขึ้น | ข้อมูลที่ควรเห็นก่อน |
|---|---|---|
| ผู้แจ้งซ่อม | แจ้งซ่อมและติดตามความคืบหน้า | งานที่แจ้ง สถานะ ผู้รับผิดชอบ |
| ช่าง | เริ่มงาน บันทึกผล แนบรูป ส่งตรวจ | งานวันนี้ ความเร่งด่วน สถานที่ ขั้นตอนถัดไป |
| หัวหน้างาน / ผู้วางแผน | จัดสรรงาน ตรวจผล และจัดการงานค้าง | งานเกินกำหนด งานรอตรวจ ผู้รับผิดชอบ |
| จัดซื้อ | จัดทำ PR/PO และติดตามเอกสาร | เอกสารร่าง รายการส่งกลับ สถานะอนุมัติ |
| ผู้อนุมัติ | ตรวจข้อมูลและตัดสินใจ | ผู้ขอ เหตุผล ยอดเงิน เอกสารแนบ ประวัติ |
| คลัง | รับของ เบิก คืน และตรวจยอด | รายการรอดำเนินการ จำนวนคงเหลือ เอกสารอ้างอิง |
| ผู้ดูแลระบบ | จัดการผู้ใช้ สิทธิ์ และข้อมูลหลัก | รายการที่ต้องแก้ไขและผลกระทบของการเปลี่ยนแปลง |

ตารางนี้เป็น persona สำหรับออกแบบ ไม่ใช่การสร้างหรือเปลี่ยน role identifiers ในระบบ ผู้ใช้หลายบทบาทต้องเข้าถึงงานทั้งหมดที่ได้รับสิทธิ์ได้

## 4. แนวทางภาพลักษณ์

ใช้ภาพลักษณ์เรียบ สะอาด เหมาะกับงานปฏิบัติการ โดยตรวจเทียบ tokens เดิมก่อนกำหนดค่าจริง

| องค์ประกอบ | แนวทาง |
|---|---|
| สี | พื้นเทาอ่อน การ์ดขาว ตัวอักษรเข้ม น้ำเงินสำหรับ action หลัก; สีสถานะแยกตามความหมาย |
| ตัวอักษร | ใช้ฟอนต์ไทยชุดเดียวกันทั้งระบบ; เริ่มจาก Tahoma ที่มีอยู่ หากจะเปลี่ยนเป็น Noto Sans Thai ให้ทดสอบไทย/อังกฤษ ความกว้างตาราง และการโหลดก่อน |
| ขนาด | เนื้อหาหลักประมาณ 16px; ตาราง desktop ใช้ 14px ได้เมื่อยังอ่านง่าย; หัวข้อมีลำดับชัด |
| ระยะ | ใช้ชุด 4/8/12/16/24/32px; ฟอร์มโปร่งกว่าตาราง |
| ปุ่ม | primary / secondary / destructive แยกชัด; เป้าหมายสัมผัสบนมือถืออย่างน้อย 44×44px และปุ่มหลักสูง 48px |
| ไอคอน | ใช้ Lucide ตามระบบเดิม; action สำคัญมีข้อความกำกับ |
| สถานะ | ใช้ badge ส่วนกลาง พร้อมชื่อสถานะ; ไม่ใช้สีอย่างเดียวสื่อความหมาย |
| ตาราง | ตัวเลขชิดขวา หน่วยและสกุลเงินชัด หัวตารางอ่านง่าย คอลัมน์สำคัญมาก่อน |
| การเคลื่อนไหว | ใช้เฉพาะ feedback สั้น ๆ และรองรับ reduced motion |

เริ่มออกแบบและตรวจรับ light theme เป็นหลัก หากคงตัวเลือก dark theme ไว้ ต้องตรวจทั้งสองธีมก่อนส่งมอบส่วนที่แก้ ไม่เพิ่มภาพตกแต่งหรือกราฟที่ไม่มีข้อมูลช่วยตัดสินใจ

## 5. แผนดำเนินงาน

### ระยะ 0 — ตรวจหน้าจอจริงและจัด baseline (P0)

- [ ] จัดบัญชีทดสอบ DEV ตามบทบาท โดยไม่บันทึกรหัสผ่านลงเอกสาร
- [ ] เดิน flow แจ้งซ่อม → WO → ส่งตรวจ และ PR → PO → รับของ ด้วยข้อมูลทดสอบ
- [ ] เก็บภาพก่อนปรับที่ความกว้าง 375, 768, 1024 และ 1440px
- [ ] จดจุดติดขัด จำนวนคลิก เวลาทำงาน และข้อผิดพลาดของผู้ใช้
- [ ] ตรวจสิ่งที่มีแล้วใน shell, badges, tables, dialogs และ dashboard เพื่อลดงานซ้ำ
- [ ] แก้ build environment ให้มี `DATABASE_URL` ที่เหมาะสม และตรวจคำเตือน workspace root จากหลาย lockfiles
- [ ] ตรวจ migration DEV เทียบ repository โดยยังไม่เปลี่ยนประวัติ migration ที่ใช้งานแล้ว

ผลส่งมอบ: รายการหน้าจอ/ปัญหาพร้อมภาพอ้างอิง, baseline งานตัวอย่าง, รายการ dependency และผล build ที่ตรวจซ้ำได้

เกณฑ์จบ: ระบุได้ว่าปัญหาใดเกิดจริง ปัญหาใดเป็นข้อเสนอ และสามารถทดสอบด้วยบัญชีที่มีสิทธิ์เหมาะสม การออกแบบสามารถเดินต่อได้ระหว่างแก้ environment แต่การตรวจรับกับ DEV ต้องรอความพร้อม

### ระยะ 1 — รูปแบบกลางและเมนู (P1)

- [ ] ทำ tokens สี ตัวอักษร ระยะ ขอบ และ focus ให้สม่ำเสมอ
- [ ] ปรับ PageHeader, Section, ActionBar, FormField, EmptyState และ ErrorState โดย reuse ของเดิมก่อน
- [ ] จัดเมนูเป็น “ภาพรวม / งานซ่อม / จัดซื้อ / คลัง / รายงาน / ตั้งค่า” เฉพาะปลายทางที่มีจริง
- [ ] แสดงเมนูตามสิทธิ์ มี active state, breadcrumb และชื่อไทยที่ตรงกัน
- [ ] คง sidebar desktop และเมนูแบบ Sheet บนมือถือ พร้อมการคืน focus เมื่อปิด
- [ ] ทำมาตรฐาน loading, pending, success, validation error, no results และ retry

ผลส่งมอบ: ตัวอย่าง component states และ shell ที่ใช้ได้กับหน้าทดลองทั้งสามกลุ่ม

เกณฑ์จบ: ใช้คีย์บอร์ดได้ เห็น focus ชัด ไม่มีหน้าล้นแนวนอนที่ขนาดทดสอบ และ URL/API เดิมยังทำงานตามสิทธิ์

### ระยะ 2 — Dashboard ที่พาไปทำงานต่อ (P1)

- [ ] วาง “สิ่งที่ต้องทำ” เหนือกราฟ พร้อมรายการงานตามบทบาทและลิงก์ไปทำต่อ
- [ ] ใช้ KPI ที่ช่วยตัดสินใจ เช่น งานเกินกำหนด งานรอตรวจ และเอกสารรออนุมัติ เมื่อมีข้อมูลรองรับ
- [ ] จำกัด KPI หลักประมาณ 3–4 ตัวต่อบริบท แล้วให้ดูรายละเอียดผ่านลิงก์
- [ ] ให้ KPI เปิดรายการที่ใช้ scope และตัวกรองตรงกัน
- [ ] ระบุช่วงเวลาและตัวกรองที่กำลังใช้อย่างชัดเจน
- [ ] แสดง empty state ต่างจากโหลดข้อมูลล้มเหลว; ห้ามแสดงศูนย์แทน error

ไฟล์เริ่มต้น: `components/dashboard/operations-dashboard.tsx`, `app/dashboard/`

เกณฑ์จบ: ผู้ใช้ทดสอบระบุงานถัดไปและเปิดงานนั้นจาก Dashboard ได้โดยไม่ต้องมีคนชี้นำ; จำนวนรายการไม่เปิดเผยข้อมูลเกินสิทธิ์

### ระยะ 3 — Work Order รายการและรายละเอียด (P1)

- [ ] จัดมุมมอง “งานของฉัน / รอดำเนินการ / ทั้งหมด” เฉพาะที่ filter/API รองรับ
- [ ] แสดงตัวกรองหลักไม่เกิน 3–4 ตัว; ย้ายตัวกรองรองเข้า panel และมีปุ่มล้าง
- [ ] เก็บ search/filter/sort/page ใน URL เท่าที่เหมาะสม และคืนตำแหน่งเมื่อกลับจากรายละเอียด
- [ ] ให้รายการแสดงเลขงาน ชื่องาน เครื่องจักร สถานะ ความเร่งด่วน ผู้รับผิดชอบ และกำหนดเสร็จ
- [ ] ใช้ card บนมือถือ โดยยังเข้าถึงรายละเอียดที่จำเป็นได้
- [ ] จัดส่วนบนของรายละเอียดเป็นสรุปงานและ action ถัดไปจาก workflow จริง
- [ ] แบ่งรายละเอียดเป็น ภาพรวม / การปฏิบัติงาน / วัสดุและเครื่องมือ / เอกสารและประวัติ โดยรักษาข้อมูลเดิมครบ
- [ ] ใช้ action bar บนมือถือที่ไม่บังเนื้อหาและไม่ชนแป้นพิมพ์
- [ ] ลดขั้นตอนบันทึกผลและแนบรูป แสดงความคืบหน้าการอัปโหลดและลองใหม่ได้
- [ ] แสดงข้อความตรงกับความสามารถจริงของ material adapter; แยกงานเชื่อม ledger ออกจาก UI

ไฟล์เริ่มต้น: `components/work-orders/work-order-list.tsx`, `work-order-detail.tsx`, `work-order-create-form.tsx`

เกณฑ์จบ: ช่างค้นงาน → เปิด → เริ่มงาน → บันทึกและแนบรูป → ส่งตรวจได้ครบ ข้อมูลเดิมไม่หายเมื่อ validation ไม่ผ่าน และไม่มี action ข้ามสถานะหรือสิทธิ์

### ระยะ 4 — PR/PO และงานอนุมัติ (P1)

- [ ] แยกมุมมองร่าง รออนุมัติ ส่งกลับ และเสร็จแล้วตามสถานะจริง
- [ ] จัดฟอร์มเป็นข้อมูลเอกสาร / รายการสินค้า / ยอดรวม / เอกสารแนบ
- [ ] ปรับตารางหลายรายการให้แก้จำนวนและราคาได้สะดวก พร้อม error รายแถว
- [ ] ใช้ searchable stock item control ที่มีอยู่ และแยกราคาล่าสุดที่ใช้อ้างอิงจากราคาที่บันทึกจริง
- [ ] แสดงยอดรวม ภาษี ส่วนลด และสกุลเงินชัดเจนตามกฎคำนวณเดิม
- [ ] จัดหน้าอนุมัติให้เห็นผู้ขอ เหตุผล ยอดเงิน รายการ เอกสารแนบ และประวัติในบริบทเดียว
- [ ] แสดงผู้อนุมัติปัจจุบันและขั้นถัดไปจากข้อมูลจริง ไม่คาดเดาสายอนุมัติ
- [ ] ใช้ปุ่มอนุมัติ/ส่งกลับ/ปฏิเสธตามสิทธิ์ พร้อมเหตุผลเมื่อกฎเดิมกำหนด
- [ ] แสดง pending ป้องกันส่งซ้ำ และจัดการเอกสารที่ถูกคนอื่นเปลี่ยนระหว่างเปิดดู
- [ ] ตรวจ document dialog และเอกสารพิมพ์ที่มีอยู่ก่อนออกแบบใหม่

ไฟล์เริ่มต้น: `components/purchasing/purchasing-workspace.tsx`, `purchase-document-dialog.tsx`, `approval-workflow-workspace.tsx`, `app/approvals/`

เกณฑ์จบ: สร้าง PR → อนุมัติ → สร้าง PO → อนุมัติ → เปิดเอกสารได้ครบ รวมกรณีส่งกลับและแก้ไข โดยยอดและสถานะตรงกับ service

### ระยะ 5 — ขยายไปคลังและข้อมูลหลัก (P2)

- [ ] ใช้รูปแบบรายการ ตัวกรอง ฟอร์ม และ feedback จากระยะก่อน
- [ ] หน้ารับของแสดงจำนวนสั่ง รับแล้ว คงค้าง รับครั้งนี้ และไม่รับ พร้อมหน่วยชัดเจน
- [ ] ตรวจยอดหลายรายการและหลายรอบรับของ รวมกรณีคืนของและรับเกิน

## 7. วิธีวัดผลกับผู้ใช้

ใช้ผู้ใช้ตัวแทนทุกบทบาทหลัก หากเป็นไปได้อย่างน้อย 2 คนต่อบทบาท ใช้ชุดข้อมูลและโจทย์เดียวกันก่อน/หลัง ตัวเลขต่อไปนี้เป็นเป้าหมายเสนอ ต้องเก็บ baseline ในระยะ 0 ก่อนยืนยัน

| ภารกิจ | สิ่งที่วัด | เป้าหมายเบื้องต้น |
|---|---|---|
| หา WO ที่ต้องทำและเปิดรายละเอียด | เวลาและการเปิดหน้าผิด | เวลามัธยฐานลดลงอย่างน้อย 25% |
| บันทึกผลพร้อมรูปและส่งตรวจ | งานสำเร็จเอง / จำนวนข้อผิดพลาด | สำเร็จเองอย่างน้อย 90% และไม่มีข้อมูลสูญหาย |
| ตรวจ PR/PO แล้วอนุมัติหรือส่งกลับ | เวลา / การย้อนเปิดข้อมูล | เวลามัธยฐานลดลงอย่างน้อย 25% |
| รับของหลายรายการ | จำนวนกรอกผิด / ยอดหลังบันทึก | ยอดถูกต้องทุกกรณีทดสอบและข้อผิดพลาดลดลง |
| กลับจากรายละเอียดสู่รายการ | filter และตำแหน่งที่คืนได้ | คืนสถานะได้ทุกกรณีที่กำหนดไว้ |

รายงานจำนวนผู้ทดสอบและจำนวนครั้งควบคู่เปอร์เซ็นต์เสมอ กลุ่มเล็กใช้เพื่อหาปัญหาและตัดสินใจปรับรอบต่อไป ไม่ถือเป็นหลักฐานแทนผู้ใช้ทั้งหมด

## 8. ลำดับชุดงานและขนาดโดยประมาณ

ขนาด S/M/L เป็นขนาดสัมพัทธ์ ไม่ใช่การรับรองวันส่ง ต้องประเมินอีกครั้งหลังระยะ 0

| ชุดงาน | ขนาด | ต้องมีมาก่อน | ผลงานที่ตรวจได้ |
|---|---|---|---|
| A: สำรวจ + build baseline | M | บัญชีและ environment ทดสอบ | ภาพก่อนปรับ / issue list / ผล checks |
| B: tokens + shell + shared states | M | A | หน้าตัวอย่างและเมนูทุกขนาด |
| C: Dashboard | M | B | งานตามบทบาทและ deep links |
| D: WO list + filters | M | B | ค้นหา กรอง และกลับรายการ |
| E: WO detail + mobile execution | L | D | flow ช่างพร้อมแนบรูป |
| F: PR/PO + approval | L | B | flow สร้าง ส่งกลับ และอนุมัติ |
| G: Inventory + masters | L | F และสถานะ migration ชัดเจน | flow รับ/คืนพร้อมยอดที่ตรวจแล้ว |
| H: UAT + เอกสาร + rollout | M ต่อชุด | ชุดงานที่จะส่งมอบ | หลักฐานตรวจรับและข้อจำกัด |

ลำดับแนะนำ: A → B → C → D → E → F → G โดยทำ H ทุกครั้งก่อนส่งมอบแต่ละชุด ไม่รอทดสอบทั้งหมดตอนท้าย

## 9. ขอบเขตที่แยกเป็นงานอื่น

- การเชื่อม WO material กับ inventory ledger รวม reservation, issue, return และ costing
- การแก้กฎอนุมัติ สถานะธุรกิจ หรือโครงสร้างสิทธิ์
- การ migrate ข้อมูลจริงและการเปลี่ยน schema ที่ deploy แล้ว
- Offline mode, push notifications, global search, saved views ข้ามอุปกรณ์ และ autosave ที่ต้องเพิ่ม backend
- การเปลี่ยนแบรนด์/โลโก้ทั้งระบบ

รายการเหล่านี้อาจช่วยประสบการณ์ใช้งาน แต่ไม่ควรปะปนกับงานปรับภาพลักษณ์จนตรวจผลกระทบไม่ได้

## 10. งานแรกที่พร้อมเริ่ม

เริ่มชุด A โดยเดินหน้าจริงของ Dashboard, WO list/detail และ PR/PO approval เก็บภาพและเวลาใช้งาน จากนั้นทำชุด B และ C เป็นรอบแรกให้ผู้ใช้เห็นรูปแบบร่วม ก่อนขยายไปฟอร์มและ workflow ที่ซับซ้อน

Definition of Done สำหรับแต่ละชุด: มีภาพก่อน/หลัง, เกณฑ์ประจำระยะผ่าน, checks ที่เกี่ยวข้องผ่าน, ผล role/mobile acceptance, เอกสารอัปเดต และระบุงานค้างอย่างชัดเจน

## บันทึกความคืบหน้า — 5 กันยายน 2026 (รอบแรก)

ผลตรวจ: TypeScript, lint และ tests ผ่าน 78 รายการ; integration tests ถูกข้าม 3 รายการ Build ผ่านโดยส่ง DEV_DATABASE_URL เป็น DATABASE_URL เฉพาะ process ตรวจ ไม่ได้เปลี่ยน environment ถาวร

ตรวจ browser ด้วย fixture จำลองชั่วคราวที่ใช้ component จริง: 375×812 และ 1440×900 ไม่ล้นแนวนอน เปิดตัวกรองได้ และไม่มี console error/warning ที่ตรวจพบ ลบ route fixture หลังตรวจแล้ว ผลนี้ยังไม่ใช่ signed-in UAT หรือหลักฐานว่าข้อมูลและสิทธิ์จริงผ่าน

งานต่อ: เก็บ baseline ด้วยบัญชีจริงทุกบทบาท, ตรวจ 768/1024px และ zoom/keyboard เพิ่ม, ทดสอบ refresh/filter กับข้อมูลจริง, แก้ deployment environment และคำเตือนหลาย lockfiles แล้วจึงตรวจรับชุด B/C ก่อนขยาย WO ยังไม่ถือว่าระยะ 0–2 เสร็จทั้งหมด
