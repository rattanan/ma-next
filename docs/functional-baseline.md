# MA Next functional baseline

## Purpose and evidence limits

This document defines the minimum behavior MA Next must preserve from the legacy PHP application. Legacy paths are relative to `aes02/`. Canonical Yii routes are inferred from controller/action naming because runtime URL configuration is absent. Database DDL, production RBAC assignments, scheduler definitions, report definitions stored in database rows, and representative outputs were not available.

`NEEDS_CONFIRMATION` means the source does not establish an authoritative rule. It is not permission to invent one. “Authenticated user” identifies the visible application boundary; exact production roles remain `NEEDS_CONFIRMATION` unless a workflow actor is explicit in code.

Classifications:

- `MUST_PRESERVE`: required domain behavior or security/integrity behavior.
- `MAY_IMPROVE_UX`: behavior must remain available, but presentation and interaction may improve.
- `OPTIONAL_FOR_PHASE_1`: evidenced behavior that may be sequenced after the first migration phase.
- `DEPRECATED_PENDING_APPROVAL`: used only where clear evidence supports retirement. No function currently meets that threshold.

Status values are `PARTIAL_TARGET`, `BASELINED_NOT_STARTED`, and `NEEDS_CONFIRMATION`.

Each record includes all required baseline fields in four compact columns.

## Cross-cutting confirmation gate

Before a `BASELINED_NOT_STARTED` or `NEEDS_CONFIRMATION` function enters implementation, obtain:

1. sanitized DDL including views, triggers, indexes, constraints, collations, and approximate volumes;
2. exported non-secret status, menu/RBAC, approval, numbering, report, translation, and scheduler configuration;
3. an actor/action permission matrix;
4. representative redacted records, attachments, API payloads, PDFs/exports, and expected calculations;
5. an agreed state-transition table, error cases, audit events, and retention rules.

Absence of those artifacts must not be converted into new business rules by implementation inference.
